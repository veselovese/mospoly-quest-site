# CLAUDE.md

Контекст для Claude Code и людей, работающих с этим репозиторием. Файл обновляется в том же PR, где меняются
архитектура, команды или договорённости, — иначе следующая сессия будет работать по устаревшим данным.

## Проект

Веб-квест для школьников на мероприятии Мосполитеха. Участник вводит имя, проходит задания по нарастающей
сложности (20–30 минут) и попадает в общий рейтинг.

- Квест «Код манула» по теме «Московский зоопарк: генетика и кодирование»: 7 заданий в 4 блоках. Концепция,
  сценарий (все тексты интерфейса) и пул заданий с форматами ответов — в `docs/zoo-quest/`.
  Прежний квест про Орлова (SQL, Python, безопасность, сети, Git) удалён, он остался в истории git.
- Этот репозиторий — только фронтенд. Бэкенд (Python, Django REST Framework, PostgreSQL) разрабатывается
  отдельно: Гертнер Андрей и Коваленко Максим.
- Задачи и комментарии руководителя (Матвей Веселов) — в таблице «Задачи (Квест сайт)»:
  https://docs.google.com/spreadsheets/d/1-cG3NJMtPt2ScjOznPb4p5kKTtjOwNnEpjAH4dTR_Ts/edit

## Команды

```bash
npm install       # package-lock.json в .gitignore — не коммитить
npm run dev       # Vite на 0.0.0.0:5173, /api проксируется на VITE_API_PROXY (по умолчанию localhost:8000)
npm run dev:mock  # то же, но без бэкенда: API отвечает мок из src/api/mock.js (режим .env.mock)
npm run build     # сборка в dist/
npm run preview
```

Переменные окружения — в `.env.example` (`VITE_API_URL`, `VITE_API_PROXY`, `VITE_API_MOCK`), личные значения —
в `.env.local`. Тестов и линтера нет: проверка — сборка и ручной прогон в браузере.

## Архитектура

- React 19 + Vite 7, иконки `lucide-react`. Все стили — в одном `src/styles.css`, без CSS-модулей
  и препроцессоров.
- `src/main.jsx` — точка входа, `ErrorBoundary` и маршрутизация по `location.pathname`: `/leaderboard` →
  `src/pages/LeaderboardPage.jsx`, остальное → квест. Роутера нет, переходы — обычные ссылки.
- `src/api/client.js` — все запросы к бэкенду (`request()`, `ApiError` со `status: 0` при отсутствии связи).
  При `VITE_API_MOCK=true` запросы уходят в `src/api/mock.js` (база в localStorage, общая для вкладок,
  с демо-участниками). Мок подгружается динамически и в обычную сборку не попадает — проверка:
  `grep demo-token dist/assets/*.js` ничего не находит.
- `src/pages/LeaderboardPage.jsx` — рейтинг, опрос `GET /api/ranking/` раз в 3 с, пауза в скрытой вкладке,
  подсветка своей строки по `?me=Имя+Фамилия`.
- `src/App.jsx` — поток экранов: нет сессии → `RegistrationScreen`, смена идёт → квест (боковая панель,
  брифинг `StoryInterlude`, окно задания `ChallengeFrame`), завершение → `FinishScreen` и сброс сессии.
- `src/quest/zooQuest.js` — тексты заданий и концовок по `task_type`: брифинг, итог, краткое условие, памятка,
  подсказки, иконка, цвет, компонент. Задания приходят с бэкенда (`GET /api/tasks/`), показываются только
  те, для которых здесь есть описание.
- `src/challenges/*.jsx` — интерактив заданий. Компонент собирает строку ответа и передаёт её в
  `SubmitAction`; правильность проверяет только бэкенд.
- `src/components/` — общие части интерфейса (брифинг, окно задания, подсказки, модалка, экраны входа и итогов).
  `ChallengeFrame` — окно задания: карточка «Задание» с кратким условием (`brief`), баллами и счётчиком попыток,
  рабочая область, памятка и подсказки; сообщение о результате попытки — под кнопкой отправки (`SubmitAction`).
- `src/session/QuestSession.js` — класс сессии участника: поля (участник с токеном, задания, решённые,
  попытки, баллы, состояние интерфейса, завершение) и методы `load/save/clear`, `register`, `loadTasks`,
  `submitAnswer`, `skipTask`, `finish`, `getSummary`. Хранится в localStorage под ключом `zoo-quest-session`
  с полем `version`; при несовместимом изменении полей увеличить `SESSION_VERSION`.
- `src/hooks/useQuestSession.js` — единственный экземпляр сессии на вкладку и хук для React
  (`useSyncExternalStore`). Компоненты меняют состояние только через методы сессии.

Деплой:
- `.github/workflows/deploy.yml`: push в `main` или `dev` → образ `ghcr.io/veselovese/mospoly-quest-site:<ветка>`
  → деплой по SSH. `main` — прод, `dev` — стейдж. Push в `dev` сразу выкатывается на стейдж.
- `Dockerfile`: сборка на `node:22-alpine`, раздача `dist/` через `nginx:stable-alpine` с `deploy/nginx.conf`
  (SPA-fallback: любой путь отдаёт `index.html`, иначе `/leaderboard` даёт 404).
- Запросы `/api` в проде должны уходить на бэкенд через Caddy — в `deploy/Caddyfile` этого пока нет.
- `deploy/`: `docker-compose.yml` и `Caddyfile` (`:80` → `frontend-prod`, `:8080` → `frontend-stage`),
  `deploy.sh` на сервере в `/opt/quest`.

## Контракт с бэкендом

Источник истины — документ «Backend (1)»:
https://docs.google.com/document/d/1fm_Te2qU-venO1RUg8qCLwjuakVoO_niPZM05p0PdNw/edit

- `POST /api/participants/` `{first_name, last_name}` → `{participant_id, first_name, last_name, token, started_at}`,
  без авторизации.
- `GET /api/tasks/` → `[{id, title, task_type, points, order}]` — только активные задания, без правильного ответа.
- `POST /api/tasks/{task_id}/attempts/` `{answer}` → `{correct, points_earned, attempts_count}`.
- `GET /api/ranking/` → `[{place, first_name, last_name, score, solved_tasks, attempts_count, time_seconds}]`,
  без авторизации.
- Авторизация: заголовок `Authorization: Token <token>`.
- Правильные ответы хранит и проверяет бэкенд (`tasks.correct_answer`), фронт отправляет строку ответа.
  Задание на бэке и его интерфейс на фронте связывает `task_type`. Формат строки ответа для каждого
  задания — в `docs/zoo-quest/tasks.md`.
- Порядок рейтинга: `score DESC, solved_tasks DESC, attempts_count ASC, time_seconds ASC`.

## Инварианты (не ломать)

- Строка ответа каждого задания должна совпадать по формату с `correct_answer` из `docs/zoo-quest/tasks.md`
  (и с `TASKS` в `src/api/mock.js`). Меняете формат — меняйте все три места и предупредите бэкенд.
- Правильных ответов во фронтенде нет, кроме мока: он подключается динамически и в сборку не попадает.
- Тексты интерфейса берутся из `docs/zoo-quest/scenario.md`: правки текста — в обоих местах.
- После любого завершения (`finish`) локальная сессия очищается (`clear`), итоги живут только в состоянии экрана.

## Решения руководителя (не пересматривать без запроса)

Из комментариев к задачам в таблице:
- Квест рассчитан на 20–30 минут. Задания идут от простых к сложным, в блоке может быть несколько заданий.
- Без сохранённого прогресса квест начинается с ввода имени, с прогрессом — с последнего шага.
- Сдаться можно в любой момент: квест завершается концовкой по сценарию, при полном прохождении — финал.
  В обоих случаях есть призыв «ищи себя на лидерборде».
- При любом завершении результат отправляется на бэк и показывается на странице, локальный прогресс сбрасывается.
- Сессия на фронте — класс с полями и методами: сохраняет в localStorage, восстанавливает, отправляет на бэк.
- `/leaderboard` обновляется без перезагрузки каждые 2–3 с. Если реже — с индикатором до следующего обновления.
- Всё должно хорошо выглядеть от 320 до 2400 px: квест открывают и с телефонов.
- На экране выполнения задания кратко дублируется его формулировка.
- Сложность заданий оценивается по 11 критериям документа «crit»:
  https://docs.google.com/document/d/1ZdDqbKwQAG-WIABJlkRRGpXWb1ZG2w5tEo_iHmD_c6M/edit

## Соглашения

- Тексты интерфейса и комментарии в коде — на русском.
- Новые npm-зависимости — только при явной необходимости, с обоснованием в описании PR.
- Адаптив (320–2400 px): брейкпоинты 1080 (боковая панель → компактная верхняя с меню), 860, 560, 360.
  `:root` масштабирует шрифт через `clamp()` на больших экранах, поэтому ширины контейнеров задаются в `rem`.
  Широкие таблицы и код прокручиваются внутри своего блока, а не всей страницей. Зоны нажатия — от 44 px.

## Подсказки со штрафом (#24, клиентская часть)

См. `docs/hint-penalties.md`: `POST /tasks/{id}/hints/`, идемпотентный номер, серверные `hint_penalty/hints_used/available_points` в `GET /tasks/`. Без политики новые подсказки не раскрываются. `QuestSession.revealHint` сохраняет только подтверждённый результат. Mock уменьшает награду/итог/рейтинг на 1 балл за каждую подсказку; рабочая политика задаётся сервером.

## Проверка изменений

- Перед коммитом: `npm run build` без ошибок.
- Изменения интерфейса проверять в браузере на ширинах 320, 375, 768, 1440 и 2400 px — без горизонтальной
  прокрутки страницы.

## Пропуск заданий (#25)

`skipped` — необратимо пропущенные задания (старые снимки version 2 получают пустой список). `taskNavigation.js` управляет открытием шагов. Пропуск показывает сюжетный итог, не вызывает attempts API и не даёт баллов. Форма ответа после пропуска недоступна; `submitAnswer` отклоняет отправку. При пропусках завершение идёт с `gave_up`, поскольку текущий API не поддерживает полный финал с пропусками. См. `docs/skip-task.md`. Проверка: `node --test tests/taskNavigation.test.js`.

## Git и процесс

- Ветка `feature/<название-задачи>` от `dev` → коммиты → push → Pull Request в `dev` с описанием задачи
  и изменений → отчёт в теме «Отчеты»: «Сделал … Задачу выполнил. Открыл PR с названием …».
  В `main` и `dev` напрямую не пушить.
- Коммиты — Conventional Commits на русском (`feat:`, `fix:`, `docs:`, `refactor:`, `ci:`), с трейлером
  `Co-Authored-By` для коммитов от Claude.
- Файлы добавлять поимённо, без `git add -A`: `dist/`, `node_modules/` и `package-lock.json` не коммитятся.
- Если доступ к `origin` только на чтение — ветка пушится в свой форк, PR открывается из форка в `veselovese:dev`.
- Личные заметки (свой форк, прогресс по задачам) — в `CLAUDE.local.md`, он в `.gitignore`.
- **IMPORTANT: Claude выполняет `git push`, форк, создание PR, команды `gh`, `ssh` и деплой только после явного
  подтверждения пользователя и называет аккаунт, от имени которого действует.** Локальные коммиты — без
  подтверждения.
- Секреты (SSH-ключи, токены, `.env`) не коммитить и не просить вставлять в чат.
